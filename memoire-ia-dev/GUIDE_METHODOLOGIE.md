# Guide de fonctionnement du pipeline

## 1. Ce que le projet mesure

Le pipeline mesure des **attributions explicites a des outils IA** presentes dans les metadonnees Git et GitHub. Il ne permet pas de prouver qu'un commit ou une pull request a ete entierement produit par une IA.

Chaque detection produit quatre colonnes :

| Colonne | Signification |
|---|---|
| `ai_attribue` | `True` lorsqu'au moins une regle explicite correspond |
| `outil` | outil associe au signal, par exemple `copilot`, `cursor` ou `codex` |
| `type_preuve` | nature de la preuve : `structurelle`, `convention_branche` ou `auto_declaration` |
| `signal_attribution` | champ ou regle qui a declenche la detection |

L'absence de signal ne signifie pas absence d'usage IA : un developpeur peut utiliser un assistant dans un navigateur puis ecrire ou adapter le resultat sans laisser de trace.

## 2. Sources collectees

Le projet utilise deux canaux qui restent separes dans les resultats :

1. **Commits locaux** : historique Git extrait avec PyDriller.
2. **Pull requests GitHub** : API REST GitHub, pour obtenir auteur, type de compte, application, branche source, titre, corps, dates et labels.

Les commits sont extraits sans token une fois le depot clone. Les PR necessitent un token GitHub dans `.env`, car l'API non authentifiee est limitee a 60 requetes par heure.

```env
GITHUB_TOKEN=ghp_votre_token
```

## 3. Regles de detection des commits

Les regles sont deterministes et se trouvent dans `src/memoire_ia_dev/detection.py`.

| Outil | Signal | Type de preuve |
|---|---|---|
| Claude Code | email `noreply@anthropic.com`, `Co-Authored-By: Claude`, `Generated with Claude Code` | auto-declaration |
| Copilot | `Co-Authored-By: Copilot` | auto-declaration |
| Aider | suffixe auteur `(aider)` ou message commencant par `aider:` | auto-declaration |
| Replit | `Generated by Replit` ou `Replit-Commit-Author:` | auto-declaration |
| Devin | email contenant `devin-ai-integration` | structurelle |

Le premier signal correspondant est conserve. Les regles ne classent pas le style du code et n'utilisent aucun modele de langage.

## 4. Regles de detection des pull requests

Les regles sont dans `src/memoire_ia_dev/prs.py`. Elles sont appliquees dans l'ordre suivant.

### 4.1 Preuve structurelle

Le pipeline cherche des comptes ou identites de committer dedies :

- `Copilot` -> Copilot
- `claudeai-v1[bot]` et variantes -> Claude Code
- `devin-ai-integration[bot]` -> Devin
- `google-labs-jules[bot]` -> Google Jules
- `cursor[bot]`, `cursoragent` et variantes -> Cursor
- `codegen-sh[bot]`, `terragon-labs[bot]`, `wildcard-ai-integration[bot]` -> outils correspondants

Un compte GitHub de type `Bot` ou une action realisee par GitHub App est conserve comme `bot_generique` si son nom n'est pas connu. Il est exporte dans `bot_generique_detecte`, mais `ai_attribue` reste `False`: un bot inconnu n'est pas une attribution IA. Les bots d'automatisation usuels (`dependabot`, `renovate`, `github-actions`, etc.) sont egalement exclus.

### 4.2 Convention de branche

Le pipeline examine la branche source (`head_ref`) :

- `codex/...` -> Codex
- `cursor/...` -> Cursor
- `copilot/...` -> Copilot

C'est une convention observable, mais modifiable par un humain. Elle est donc exportee avec `type_preuve = convention_branche`, distincte d'une preuve structurelle.

### 4.3 Auto-declaration dans le texte

Le titre et le corps sont examines pour :

- lien `chatgpt.com/codex` -> Codex ;
- lien `cursor.com/agents` ou `cursor.com/bc` -> Cursor ;
- trailers ou signatures des regles de commit, par exemple Claude, Copilot ou Replit.

Ces liens sont des declarations ajoutees par les agents. Ils sont utiles mais dependants des conventions de chaque outil.

## 5. Point de bascule interne

La commande `bascules` cherche la premiere date d'ajout d'un fichier de configuration IA dans l'historique Git :

- `CLAUDE.md`, `.claude/`
- `copilot-instructions.md`, `.github/copilot-instructions.md`
- `.cursorrules`, `.cursor/rules/`
- `.aider.conf.yml`, `.replit`, `AGENTS.md`, `.devin.yaml`

Cette date est une candidate au point de bascule. Elle doit etre documentee dans `config/repos.csv` et, idealement, triangulee avec une annonce publique ou une discussion du projet.

## 6. Procedure pour analyser un depot

### 6.1 Ajouter le depot au manifeste

Renseigner `config/repos.csv` avec le nom `organisation/depot`, son URL, une date de bascule et la source de cette date.

### 6.2 Cloner et analyser les commits

```powershell
cd C:\Users\Baptiste\Desktop\Memoire\Dev\memoire-ia-dev
git clone https://github.com/organisation/depot.git .work\depot
.\.venv\Scripts\memoire-ia-dev.exe bascules .work\depot
.\.venv\Scripts\memoire-ia-dev.exe commits .work\depot data\raw\depot_commits.csv --since 2023-01-01 --until 2025-12-31
```

Le CSV de commits contient notamment dates, message, auteur, taille, merge, outil detecte et type de preuve.

Pour un historique tres volumineux, ajouter `--fast`. Cette variante utilise `git log` et conserve les metadonnees, les merges et les attributions, mais ne calcule pas les tailles de diff. Elle convient aux series trimestrielles d'adoption, pas a l'analyse de granularite des commits.

### 6.3 Analyser les pull requests

Creer `.env` a partir de `.env.example`, ajouter le token, puis lancer :

```powershell
.\.venv\Scripts\memoire-ia-dev.exe prs organisation depot data\raw\depot_prs.csv --since 2023-01-01 --until 2025-12-31
```

Le CSV de PR conserve `head_ref`, le titre, le corps, les dates, le compte auteur, le type de preuve et le signal declencheur. Il faut conserver le fichier brut avant tout filtrage.

GitHub ne filtre pas les PR par date dans cet endpoint. Le pipeline demande donc les pages triees par date de creation decroissante, conserve uniquement les PR entre `--since` et `--until`, puis s'arrete lorsque la borne basse est atteinte. La periode est donc definie par `created_at` pour les PR et par la date auteur pour les commits.

### 6.4 Reprendre apres un quota API ou decouper la collecte

Chaque page GitHub contient au plus 100 PR. Le CSV et un checkpoint sont ecrits apres chaque page terminee. Pour ne traiter que cinq pages lors d'une premiere session :

```powershell
.\.venv\Scripts\memoire-ia-dev.exe prs organisation depot data\raw\depot_prs.csv --since 2023-01-01 --until 2025-12-31 --max-pages 5
```

Le fichier `data/raw/depot_prs.checkpoint.json` indique la page suivante. Pour continuer exactement la meme fenetre lors d'une session ulterieure :

```powershell
.\.venv\Scripts\memoire-ia-dev.exe prs organisation depot data\raw\depot_prs.csv --since 2023-01-01 --until 2025-12-31 --resume
```

`--resume` refuse de continuer si le depot ou les bornes de date different, ce qui protege la reproductibilite. Le checkpoint est supprime automatiquement lorsque la fenetre est terminee.

Pour voir la progression sans appeler GitHub ni consommer de quota :

```powershell
.\.venv\Scripts\memoire-ia-dev.exe status data\raw\depot_prs.csv
```

La commande indique le nombre de PR sauvegardees, les dates actuellement couvertes, les attributions explicites trouvees et, si la collecte est incomplete, la page GitHub a reprendre. Ajouter `--json` pour reutiliser ce statut dans un script.

## 7. Nettoyage et metriques

`cleaning.clean_commits()` ajoute, sans supprimer de lignes :

- `bot_automation` ;
- `taille` et `taille_aberrante` ;
- `categorie_tache` : `fix`, `feat`, `refactor`, `docs`, `test` ou `other`.

Les commits de merge sont exclus pour les metriques de taille. Le module `metrics.py` calcule les compteurs annuels, trimestriels (`annee_trimestre`, par exemple `2024Q1`) et les comparaisons avant/apres. Le module `analysis.py` applique Mann-Whitney U et une taille d'effet rank-biserial.

Pour l'evolution historique a partir de 2020, privilegier `build_quarterly_summary()` : il conserve assez de granularite pour voir une adoption progressive tout en restant plus stable qu'un comptage mensuel. Garder la meme granularite sur tous les depots et comparer commits et PR dans deux series distinctes.

Les volumes de commits et de PR ne doivent pas etre fusionnes : ce sont deux canaux d'observation differents.

## 8. Validation contre AIDev

AIDev est un corpus public de PR deja attribuees a des agents. La commande suivante evalue toutes ses PR :

```powershell
.\.venv\Scripts\memoire-ia-dev.exe eval-aidev data\processed\aidev_full_report.json --records-output data\processed\aidev_full_records.csv
```

Elle produit :

- `data/processed/aidev_full_report.json` : rappel global et rappel par outil ;
- `data/processed/aidev_full_records.csv` : resultat ligne par ligne pour audit.

Resultat de la derniere execution :

| Outil | PR AIDev | PR detectees | Rappel |
|---|---:|---:|---:|
| Claude Code | 18 232 | 17 064 | 93,59 % |
| Copilot | 349 695 | 345 027 | 98,67 % |
| Cursor | 212 544 | 168 821 | 79,43 % |
| Devin | 43 298 | 43 298 | 100,00 % |
| Google Jules | 50 490 | 50 449 | 99,92 % |
| OpenAI Codex | 2 069 595 | 1 970 339 | 95,20 % |
| Total | 2 743 854 | 2 594 998 | 94,57 % |

Pour Cursor, le rappel conditionnel atteint 97,68 % quand AIDev fournit les donnees de commit. Son rappel brut est plus bas parce que cette table ne couvre que 1,91 % de ses PR.

## 9. Ce que ces resultats permettent et ne permettent pas de dire

Le test AIDev donne un **rappel** : parmi les PR positives du dataset de reference, le pipeline retrouve 94,57 % des attributions. Il ne donne pas une precision valide, car AIDev ne contient pas un echantillon de PR negatives certifiees humaines.

Pour mesurer la precision :

1. Tirer un echantillon de PR detectees et non detectees hors AIDev, par depot et par outil.
2. Verifier manuellement comptes, application, branche, texte, commits et liens.
3. Etiqueter `attribution_explicitement_presente`, `attribution_explicitement_absente` ou `indetermine`.
4. Rapporter le nombre de cas indetermines et calculer la precision sur les cas verifiables.

Ne pas presenter 94,57 % comme une certitude sur l'origine du code. La formulation correcte est : le detecteur retrouve 94,57 % des attributions explicites presentes dans AIDev, selon les regles et la version du dataset utilisees.

## 10. Reproductibilite

- Executer les tests :

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

- Versionner `config/repos.csv`, les regles de detection et les scripts.
- Ne jamais versionner `.env`, le token, les clones complets ou les sorties brutes volumineuses.
- Noter la date d'execution, la version d'AIDev et les changements de conventions des outils.
- Refaire la validation AIDev apres toute modification des regles.
